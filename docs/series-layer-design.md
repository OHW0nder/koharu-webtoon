# 漫画 / 章 / 页 三层方案

本文是本地扩展的设计决策记录。扩展的形态约束见 `docs/extending-koharu.md`：核心原则是只新增、不修改内核既有结构。

目标是把「漫画」与「章」变成可管理的一级与二级对象，页仍是内核的原生单位，并且给未来的漫画级翻译资料（翻译指导、术语表）留出位置。

---

## 1. 章项目为什么可以嵌在漫画目录下

这一节原先的前提是「项目名是内核唯一稳定的公开标识」，因此章项目必须平铺在库根下。那个前提不成立：

- `koharu_storage::Session::create` / `open` 只收一个路径，从不检查目录名
- `StoredState.document` 是 `Session::create` 时生成的 `DocumentId`（UUID v7），**与路径和名字都无关**；`Session::save` 只校验它与句柄一致
- `.khrproj` 后缀只出现在 app 层（`ProjectLibrary::resolve` 与 `list`），存储层完全不认识

也就是说内核的项目身份本来就是 `DocumentId`，目录名一直是 app 层的查找键。既然如此，「漫画目录 / 章目录」两级布局就是纯 app 层的约定，不需要内核配合。

平铺还带来一个必须绕开的坑：章项目名要拼成 `<漫画名> Ch<NN>` 才能自带归属，而这个名字**没有去重**。两部漫画 `sanitize` 后同名（`A/B` 与 `A-B`，或两部都叫 `Demo Title`）时，第二次导入会硬失败在 `Session::create` 的 `project already contains a state`，不是去重也不是自动加后缀。按漫画分层之后路径天然隔离，这类冲突从根上消失。

结论：**漫画目录是库根目录的直接子目录，章项目在漫画目录之下**，章目录名只用序号 `Chapter <seq>`。

## 2. 三层的落位

```
Documents/Koharu/                  ← 库根目录，用户可在设置里指定
  Demo Title/                      ← 第一层：漫画，库根目录的直接子目录
    series.json                    ← 章索引 + 封面 + 漫画级配置
    cover.jpg                      ← 可选，用户未指定时不存在
    glossary.json                  ← 术语表
    context-<seq>.json             ← 章外上文，按目标章序号命名
    Chapter 22/                    ← 第二层：章项目，就是内核眼里的普通项目
      state-a.khr
      state-b.khr
      blobs/
      project.lock
  Demo Title Ch23.khrproj          ← 不再存在
```

章目录名只有序号，所以认章的依据是目录形状：含 `state-a.khr` 或 `state-b.khr` 的目录就是章项目，索引、术语表、旁挂文件自然被排除，`.khrproj` 后缀因此没有存在意义，已删除。

`ProjectLibrary::list` 遍历两层而不是查索引，因为索引可能正好是缺的那一份（导入在写索引前中断，或索引被手工删掉），而残骸清理正依赖这个枚举。

封面文件不存在时，前端渲染内置占位图，不产生任何磁盘写入。

第三层是页，完全不动：`State::page_order`、`Edit::add_page`、页面栏、检测/OCR/翻译流水线全部保持现状。

## 3. series.json

漫画层的数据全部落在这里，与任何章项目解耦：删除一章不影响漫画定义，删除漫画不影响章项目。

```json
{
  "schema": 1,
  "id": "love-quest",
  "title": "Demo Title",
  "serial": true,
  "cover": null,
  "source_root": "<下载目录>\\demo-title",
  "chapters": [
    {
      "seq": 22,
      "title": "Chapter 22",
      "project": "Demo Title Ch22",
      "source": "Chapter 22",
      "kind": "webtoon",
      "status": "done"
    }
  ],
  "settings": {}
}
```

设计要点：

- `serial` 区分连载与单行本。它由导入时的目录结构自动判定（见 §3.1），只影响界面呈现：连载列出全部章，单行本始终只有一章。
- `cover` 存封面文件名而非路径。`null` 表示用户没有指定，前端渲染占位图；指定时文件就在漫画目录内，因此删漫画会一并删掉封面，不会留下悬挂引用。
- 章引用的是**项目名**而非路径。项目名是内核唯一稳定的公开标识，将来若官方做了章节容器，可以据此把索引搬进官方结构，不需要重新扫描。
- `source` 存相对 `source_root` 的路径。绝对路径只出现在漫画级的 `source_root` 一处，迁移整部漫画时只需改这一个字段。
- 章级的 `kind` 记录这一章的源形态，取值 `manga`（页漫：多张普通页）与 `webtoon`（条漫：一张纵向长图）。它决定导入时是否切页，是导入那一刻的判断，记录下来是为了让界面与批量处理知道这一章的处理依据，也是将来官方实现章节管理时可直接映射的字段。**章级用 `kind`、漫画级用 `serial`，两者不混用。**
- `status` 是漫画层的编排状态，与章项目内部的处理状态分离。取值 `pending | imported | done`，用于批量操作时筛选目标与展示进度。
- `settings` 是漫画级配置的归位。翻译指导与广告高度进这里；术语表条目多且改动频繁，作为同目录的独立文件，由 `settings` 引用文件名。**空对象即可，本期不实现。**

章序号 `seq` 允许不连续（连载中间补番），排序一律按 `seq`，不依赖数组顺序。

### 3.1 导入时自动判别连载与单行本

选定一个文件夹后，看它有没有子文件夹：

```
demo-title/                 判定：连载
  Chapter 22/               → 一章
  Chapter 23/               → 一章

阿伦的烦恼/                  判定：单行本（没有子文件夹）
  001.jpg …                 → 一章，章名取文件夹名
```

判别只看一层子目录，不递归。这是刻意的：一个塞满图片的下载目录与一个按章分好的下载目录，区别就在这一层。

单行本也会建成漫画，只是 `serial: false` 且 `chapters` 只有一个元素，章的 `title` 跟随文件夹名。这样两类作品在首页、章节管理、批量操作上共用同一套代码，界面不需要为单行本开特例分支。

## 4. 新增命令

全部是新增，不触碰既有命令签名。

| 命令 | 职责 |
| --- | --- |
| `import_series` | 导入一个文件夹作为漫画，按有无子目录自动判别连载或单行本 |
| `list_series` | 读出全部漫画及其章摘要，供首页漫画柜展示 |
| `import_series_chapter` | 为已有漫画导入新章（`kind` 决定走页漫还是条漫） |
| `set_series_cover` | 指定或清除某部漫画的封面 |
| `rename_series_chapter` | 改章标题与序号 |
| `scan_series_source` | 扫 `source_root`，把尚未登记的章目录列出来 |
| `process_series_chapters` | 对选中的章依次执行处理作业 |
| `export_series_chapters` | 对选中的章依次导出 |
| `delete_series_chapter` | 移除章条目；是否连带删除章项目由调用方显式指定 |

封面是漫画级数据，所以 `set_series_cover` 属于这一层。它把一张图片复制进漫画目录并记录文件名；清除只是把 `cover` 置回 `null`，不删文件。

### 4.1 导入一章：类型是导入时选定的

章的源形态决定它怎么进项目，这由用户在导入时选择，不靠猜：

| 类型 | 源目录形态 | 导入路径 | 切割 |
| --- | --- | --- | --- |
| 页漫 `manga` | 多张普通页图 | 现有 `import` | 不切，每张图一页 |
| 条漫 `webtoon` | 一张纵向长图 | 现有 `import_webtoon` | 按可读高度切页 |

两个选项正好对应两条既有的导入路径，底层函数与对外行为都不变；新流程只是让用户在创建章之前明确选一次，并把结果记进索引的 `kind`。

选择必须显式而不是自动判定：条漫的典型形态（极高长图）能被几何门限自动识别，但页漫里也存在高幅面的单页，自动判定会在两类之间误判，而误判的代价是整章被切碎或完全没切。

导入时顺带把「识别漫画与章」也交出去：如果 `source_root` 下有 `Chapter 23` 这样的子目录，导入界面应当直接列出候选章让用户勾选，而不是要求用户逐个进目录。

### 4.2 批量处理与单活动项目

内核同一时刻只允许一个活动项目：`CurrentProject` 是 `Mutex<Option<Project>>`，`process` 命令直接取 `State<CurrentProject>`。所以批量必须**串行**：

```
for 章 in 选中章:
    open_project(章.project)
    process(scope = Project, operation)
    等待 Job 结束          // 轮询 Processing.jobs 或订阅 JobChannel
    导出（可选）
    close_project()
```

`replace_project` 在切换时已经会停掉在跑的作业、清空 job、重置 agent，所以串行循环是安全的。每章独立提交，中断后可从未完成的章续跑。

进度通过现有的 `JobChannel` 往上汇报，前端只需显示「第 3 / 12 章 · 检测中」。

### 4.3 对接自动下载

`source_root` 记的就是下载器的输出目录。`scan_series_source` 列出其中尚未登记的子目录，用户确认后逐个 `import_series_chapter`，新章状态为 `pending`，随后被批量处理纳入。

这一层刻意保持手动确认而非全自动：切页阈值与切割边界是会影响译文的判断（见 `docs/reference/koharu-webtoon-support.md` 的限制表），不适合无监督执行。下载本身交给 manga-dl，应用只负责发现与登记。

## 5. 漫画级翻译资料的预留

翻译指导与术语表归属漫画层。**注入方案经审计后已修正**：`instructions` 是全局配置，直接填进去会写进用户的 `config.toml` 并在多部漫画之间串味。正确做法是用 `Config::memory` 为每部漫画构造一条作用域受限的处理管线，批量开始前换上、结束后恢复。

完整审计、事实链与代价见 `docs/series-translation-assets-audit.md`。要点：

- 术语表存漫画目录的独立文件（`glossary.json`），与 `series.json` 同级
- `SeriesSettings` 存翻译指导与术语表引用，不存渲染好的文本
- 编辑入口在章节管理页（第二层），不在设置页
- `koharu-pipeline` 与 `koharu-scene` 仍然一行不改

**角色卡不做。** 切片无法保证把说话人完整地留在同一页——气泡的尖尾可能落在上一页，人脸可能被刀口分开。说话人归属本身不可靠，描述「谁用什么语气说话」的资料没有可靠锚点。术语表不受影响：词条靠文本匹配定位，与说话人归属无关。

### 5.1 漫画级翻译指导

漫画层需要一份**手写的翻译指导**，用来表达这部作品特有的风格约定——例如「不用敬语」「保留日语式停顿」「专有名词一律意译」。不同作品的风格差异是常态，单靠全局指导覆盖不了。

它与术语表并列，同样在章节管理页编辑，同样由作用域管线渲染进 `instructions` 字段。全局指导保留，排在漫画级指导之后，作为跨作品的个人口味兜底。

三段内容的拼接顺序与上下文注入方式见 `docs/reference/koharu-glossary-design.md`。该文档同时覆盖上下文（章内回溯与跨章上文），并给出了跨章上文按**章序号**判定的规则：上一章永远是序号相邻的那一章，与用户勾选和执行的顺序无关。

### 5.2 条漫广告带

条漫下载产物的首尾各有一段固定高度的站点广告，其中的文字不需要翻译。**在导入时把这两段从源图裁掉**，再走正常的切片与流水线。设计见 `docs/reference/webtoon-ad-bands-design.md`；三项漫画级设置的统一入口见 `docs/series-settings-design.md`。

广告高度存**漫画级**，存在漫画索引里，不存章项目——因为它必须在导入动作发生时被读取，而首次导入时章项目还不存在。新增章节默认沿用该值，并提供逐次关闭的开关。

首条高度自源图顶端起算，尾条高度自底端起算，均为原始源图像素。锚定底端是必需的：每章总高不同，从顶端算的位置会随章节长度漂移。

裁掉的部分直接丢弃，因此**导出结果不含首尾广告**。裁剪发生在切片之前，所以批处理路径完全不变——不需要按过滤后的页列表运行，批量命令与进度汇报都保持原样。

## 6. 前端

三层各自对应一个界面，库根下的平铺项目列表的职能被接管：

```
漫画柜（StartView）              一级：封面网格
  └─ 点封面 → 章节管理（SeriesView）   二级：章列表
       └─ 点章 → 编辑器（现有界面）      三级：页
```

**漫画柜**取代原先平铺在库根下的项目列表。每部漫画一张封面卡片，未指定封面时渲染内置占位图。顶部是「导入漫画」入口，选一个文件夹即完成判别与建库。还没有被任何索引认领的章收进「孤立章」一组——**只有清理，没有打开**（残骸多半是导入中断或索引被删造成的，里面没有可编辑的完整状态）。

**章节管理**列出该漫画的章。章可多选，批量操作（翻译 / 导出 / 标记状态）。单行本在这一层只有一章，与连载共用同一套组件。顶部提供「导入新章」与「设置封面」。

**编辑器**完全保持现状。进入路径从漫画柜改为经章节管理点入，其余交互不变。

原始导入菜单（标题栏「导入」子菜单、页面栏空状态下拉）全部移除，导入能力由漫画柜与章节管理承接。底层 `import` 与 `import_webtoon` 命令保留不动。

漫画柜需要 `list_series` 返回：漫画 id、标题、`serial`、封面文件名、章数与已处理章数。章节管理需要各章的 `seq` / `title` / `kind` / `status`。**页数要新开一个轻量查询**，因为现有 `get_pages` 绑定当前项目、只对活动章有效。

章在前端以 [`ChapterRef`]（漫画目录名 + 章目录名）出现，而不是一个字符串：章目录名只有序号，父目录才是它唯一的归属信息。

## 7. 风险对照

| 内容 | 触碰官方 | 说明 |
| --- | --- | --- |
| `series.json` 读写 | 否 | 旁挂文件 |
| 章项目目录布局 | 否 | 内核只收路径，`DocumentId` 与路径无关 |
| 库根目录可配置 | 否 | 只改 `ProjectLibrary` 解析默认值的位置 |
| 6 个新命令 | 否 | 只新增 |
| `import` / `process` / `export` 签名 | 否 | 不动 |
| StartView 漫画视图 | 否 | 前端独立 |
| 术语表与翻译指导注入 | 否 | 复用现有 `instructions` 字段 |
| 漫画级翻译指导存储 | 否 | 旁挂索引字段 |
| 上下文注入 | 否 | 同上；跨章上文走旁挂文件 |
| 广告带裁剪 | 否 | 导入时裁掉源图首尾，批处理路径不变 |
| `koharu-scene` | 否 | 零改动 |
| `open_project` / `delete_orphaned_project` | 否（删除） | 契约已不成立，由 `open_chapter` / `delete_orphaned_chapter` 取代 |
| 章目录名允许路径分隔符 | 否（本地收紧） | 漫画目录名与章目录名各过一遍 `validate_directory_name` |

`koharu-scene` 相对上游仍然只有 `Assets` 的一处可见性提升。

原先这张表里的两条红色（项目名允许路径分隔符、`list()` 递归扫描）都源于「章项目必须平铺」这个前提，前提不成立后它们不再成立：嵌套布局没有放宽任何内核校验，`validate_directory_name` 反而比原来的 `validate_project_name` 更严格——它现在同时守住两段路径。

## 8. 实施顺序

1. **done** — series 存储层：读写 `series.json`、schema 校验、连载与单行本的判别 + 单元测试
2. **done** — `import_series` / `list_series` / `get_series`：导入一个文件夹，漫画柜显示封面卡片
3. **done** — 章节管理视图：列出章、点入编辑器；旧的导入菜单已移除
4. **done** — `scan_series_source` 与 `import_series_chapter`：扫描下载目录，勾选新章并指定条漫或页漫
5. **done** — `process_series_chapters` 与 `export_series_chapters`：批量翻译与批量导出
6. **未做** — 设置封面。卡片目前固定渲染占位图，索引里的 `cover` 字段已就位
7. **未做** — 翻译指导与术语表（位置见 §5）
8. **未做** — 条漫广告带裁剪（§5.2）
9. **未做** — 翻译上下文注入：章内回溯与跨章上文（`docs/reference/koharu-glossary-design.md`）

覆盖到的完整链路：导入一个漫画文件夹 → 看到封面卡片 → 进章节列表 → 勾选若干章 → 批量翻译 → 批量导出到一个目录。连载后续更新时，扫描源目录会列出 manga-dl 新下的章，指定类型后追加进同一部漫画。

批量是**串行**的：内核同一时刻只允许一个活动项目和一个作业，所以实现为「开一章 → 跑完整项目范围 → 等作业结束 → 下一章」。每章独立提交，中断后重跑未完成的章即可。导出同样串行，共享 `export_snapshot` 这一个实现，单章导出与批量导出产生逐字节一致的结果。
