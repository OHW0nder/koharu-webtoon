# 扩展开发指导

本文件是本仓库开发非上游功能时的长期约束。它回答一个问题：**如何实现自己的功能，同时不制造与上游合并的冲突，使得上游将来实现同类功能时可以直接放弃本地实现。**

不记录具体实现细节与文件行号，只记录判定规则。外部实现的调研材料放在 `docs/reference/`，那类材料是参考输入，不是待实现的规格。

---

## 1. 核心原则

**只新增，不修改。**

本地实现应当落在内核已经预留的扩展点上，而不是改动内核既有的数据结构。判断标准是：上游对某个文件做重构时，本地改动是否会变成文本冲突或语义冲突。

违反这条原则的成本不是当下的编译错误，而是未来必须二选一：要么放弃本地功能，要么长期分叉。两者都不可接受，因此规则是硬性的。

---

## 2. 扩展点契约

场景内核（`koharu-scene`）在设计上对第三方组件开放。内核的组件校验对未注册的 kind 兜底放行，并保留其 schema 版本、引用与指纹，所以官方版本加载含本地组件的项目不会失败，也不会丢失数据。

### 2.1 自定义组件

实现 `Component` trait 即可，无需修改内核任何文件。

trait 提供：

- `const KIND: &'static str` —— 组件身份
- `fn record_refs(&self) -> Vec<EntityId>` —— 声明引用的实体，供内核追踪
- `fn blob_refs(&self) -> Vec<BlobId>` —— 声明依赖的 blob，供垃圾回收正确工作
- `fn validate(&self, context) -> Result<()>` —— 校验，可用 context 检查实体与 blob 是否存在

trait bound 要求 `SerializeRevisioned + DeserializeRevisioned`，即必须用 `revision` crate 提供的派生宏，序列化格式由该 crate 定义。

### 2.2 写入与读取

| 操作 | API |
| --- | --- |
| 写实体组件 | `Edit::set::<T>()` |
| 写项目组件 | `Edit::set_project::<T>()` |
| 写关系组件 | `Edit::set_relation::<T>()` |
| 删实体 / 项目 / 关系组件 | `Edit::remove::<T>()` / `remove_project::<T>()` / `remove_relation_component::<T>()` |
| 读实体组件 | `Snapshot::component::<T>()` |
| 读项目组件 | `Snapshot::project_component::<T>()` |
| 读 blob 字节 | `Snapshot::read_blob()`（异步） |
| 枚举页面 | `Snapshot::pages()` |

读取返回 `Result<Option<T>>`，`None` 表示该实体上没有此组件，这是扩展读取的正常分支，不是错误。

### 2.3 自定义关系

关系不是组件，而是独立的全局表。实现 `RelationSpec` 并声明 `KIND` 即可，无需修改内核的关系定义。需要函数性（一源一目标）时另实现 `FunctionalRelation`。

写入用 `Edit::relate::<R>()`，删除用 `Edit::remove_relation()`。

未注册关系的端点校验同样兜底放行，因此自定义关系不会因内核不认识而被拒绝。

### 2.4 命名空间

组件 kind 与关系 kind 都强制包含 `.`，且每一段只能是 ASCII 字母数字与 `-`、`_`，总长不超过 255。

这意味着**不要使用 `dev.koharu.*` 前缀**。该前缀属于上游，本地实现应使用能标识自己的独立前缀，并且一旦确定就不再变更——改名会导致既有数据中的组件无法被识别。

### 2.5 持久化保证与失效边界

内核为每个组件独立存储 schema 版本号，序列化按该版本迁移。因此：

- 上游修改自己的组件，不影响本地组件的版本与可读性
- 本地组件自身升级时，必须按 `revision` 的迁移机制递增版本，不能直接改结构
- 反序列化时内核拒绝版本号为 0 或高于当前实现的组件。跨版本兼容的责任在组件自身的迁移实现上

### 2.6 两个必须遵守的门禁

`record_refs` 与 `blob_refs` 的一致性是硬校验：组件声明的引用集合必须与存储中的记录完全一致，否则报引用不匹配，**项目将无法打开**。

由此产生两条实践要求：

- 声明了 `record_refs` 的组件，在相关实体被删除后必须同步清理悬空引用，且清理必须与删除操作处于同一次提交
- 声明了 `blob_refs` 的组件，其 blob 在垃圾回收时会被正确保留或释放；漏声明会导致数据被提前回收或无法回收

### 2.7 已知缺口

`Assets` 组件类型目前未从 `koharu-scene` 的公开导出中导出（其 `Asset`、`AssetRole`、`AssetMetadata` 已导出）。需要按 blob 读取页面原始像素的实现会遇到这个缺口。

解决方式是把 `Assets` 加入 `koharu-scene` 的导出列表——这是一处可见性改动，不改变任何数据结构或行为，风险接近于零，属于允许的例外。禁止的做法是为了绕过它而复制一份资产结构定义。

## 3. 风险分级

改动位置决定了未来的冲突概率。提交前对照本表自查。

### 3.1 绿色：可自由改动

- 新增 crate、新增模块、新增纯算法
- 自定义组件、自定义关系
- 新增 Tauri 命令（只新增，不改既有命令签名）
- 前端新增独立功能

### 3.2 黄色：需要理由，并记录理由

- 既有函数的内部实现（尤其是可被上游重写的流程性代码）
- 既有 Tauri 命令**新增可选参数**（会使生成的前端协议文件过期，必须同步重新生成）
- 既有处理阶段的内部逻辑

黄色改动的判定标准：上游重写同一处逻辑时，本地改动是否还有意义。若没有，则应考虑上移到自定义组件表达。

### 3.3 红色：禁止

- 场景内核的 `State` 结构（新增顺序向量、字段等）
- 组件注册表（把自定义组件登记进官方组件表）
- 组件与关系的公开导出列表（仅允许 2.7 例外那种可见性补充）
- 既有组件的字段（除非按 `revision` 机制做版本演进）
- 既有 Tauri 命令签名（增删参数）
- 页面顺序的语义

红色的判定标准：这些位置定义了上游的公开契约，本地改动与之竞争同一命名空间或同一语义，必然产生冲突。

## 4. 页面结构类功能的实现约束

项目当前只有「项目 → 页面列表」两层语义，且被上游明确为刻意设计（导入时拒绝发明章节编号）。若要表达漫画、章节、卷这类内容层级，**不得**通过修改页面顺序结构实现。

正确做法是把层级表达为一个自定义项目组件，其中保存章节条目与页面实体的对应关系，页面顺序保持由内核独占。

由此产生的义务：

- 页面顺序仍由内核持有，自定义组件只是对它的引用视图。两者必须提供一致性校验，并在不一致时以明确方式失败，而不是静默使用旧映射
- 删除、移动页面时必须同步更新该组件的引用集合
- 页面顺序的乐观并发令牌由内核维护；自定义组件派生出的顺序在并发提交后可能过期，不得假设它总是最新

## 5. 与上游的同步策略

### 5.1 同步频率

本地不长期脱离上游。以可编译、可运行的最小单元定期合并上游主干，冲突成本远低于积累数月后一次性解决。

### 5.2 合并顺序

先解决构建与测试通过，再处理行为差异。合并后必须验证自定义组件的数据仍能被读取——这是扩展点契约是否仍然成立的唯一实际检验。

### 5.3 上游实现同类功能时

不要试图让两套实现共存，也不要把本地实现改造成上游的形状。默认动作是**放弃本地实现，迁移数据**：

1. 本地组件的持久化数据仍可读取，因为内核对未知组件宽容
2. 编写一次性迁移脚本，把本地组件的数据写入上游组件
3. 删除本地组件的读写代码

为此，从一开始就把本地组件的数据结构设计成**能无损映射到上游可能的实现**：使用上游已有的实体标识与概念，避免引入只有本地才有的中间概念。这样迁移是数据搬运，而不是重新翻译。

### 5.4 判定「本地实现是否还有价值」

上游同类功能可用后，本地实现的价值只剩下上游尚未覆盖的部分。逐项对比后保留差异部分，删除已覆盖部分。不要因为已经投入了开发成本就保留冗余实现——两套术语表或两套章节结构并存，比缺少功能更糟。

---

## 6. 提交前自查

- 新增的组件与关系是否使用了非上游的命名空间前缀
- 自定义组件的版本号是否按 `revision` 机制管理
- 声明的 `record_refs` 是否在相关实体删除时被同步清理
- 声明的 `blob_refs` 是否完整，垃圾回收行为是否正确
- 是否改动了任何红色位置；若有，是否能用自定义组件达到同样目的
- 是否修改了既有 Tauri 命令签名；若有，前端协议文件是否已重新生成
- 数据结构是否记录了上游实体的标识，以便未来迁移
