# 项目级术语表与角色卡：设计

本文记录本仓库拟实现的翻译辅助功能的设计判定。判定依据是本仓库自身的约束（见 `docs/extending-koharu.md`）与对外部三个参考实现（`xianscan-webtoon-pipeline.md`、上游 PR #1097 / #1137、社区 fork）的调研。

本文只记录设计判定与理由，不记录实现进度。

---

## 1. 四个概念的边界

调研中反复出现的其实是四个不同的东西，它们的生命周期、作用域和注入通道都不同。混在一起是需求反复变形的主要原因，因此先固定边界。

| 概念 | 内容 | 作用域 | 生命周期 | 注入通道 |
| --- | --- | --- | --- | --- |
| **翻译指导** | 用户手写的自由文本：风格、语气、禁止项 | 全局 | 长期，跨项目 | 附加说明 |
| **术语表** | 原文到定稿译文的硬约束，逐条成对 | 项目 | 随项目，人工维护 | 语境条目 |
| **角色卡** | 整部作品的人物、称呼关系、语气约定、专有词解释。自由文本 | 项目 | 随项目，人工维护 | 附加说明 |
| **上下文滑窗** | 前若干页已翻好的原文与译文对照 | 运行时派生 | 每次运行重新计算，不持久化 | 语境条目 |

四条判定：

1. **术语表与角色卡是项目数据，翻译指导是应用设置。** 术语与人物设定是作品固有信息，换一本书就失效；翻译指导是用户对机器翻译的个人口味，可以跨作品复用。因此前两者存场景组件，后者留在全局配置。
2. **上下文滑窗不持久化。** 它完全由场景中已有的译文派生，存下来会产生第二份真相。人工修改过的译文优先级高于生成的译文，这条规则由场景的来源机制已经保证，滑窗直接利用它，不需要额外字段。
3. **术语表与角色卡分成两个组件。** 两者虽然都进同一个请求、同一个面板，但形状不同（结构化条目 vs 自由文本），演进节奏也不同。分开后术语表可以保持为上游可能实现的镜像，迁移时是数据搬运。
4. **翻译指导维持全局，不做项目级覆盖。** 现有界面与文档都明确它是全局的（设置页的说明文字写着对每个项目生效）。为它引入项目级覆盖会带来两级配置与「为什么这条没生效」的排查成本，收益不成比例。

## 2. 存储

### 2.1 组件定义

两个项目级自定义组件，放在流水线 crate 内的新模块。放在流水线 crate 的原因是注入发生在翻译阶段，而界面层通过重新导出访问同一定义；流水线是两者中更底层的一层。

- 术语表：组件 kind `dev.koharu.glossary`
- 角色卡：组件 kind `dev.koharu.translation.note`

不放入场景内核、不登记进组件表、不加入公开导出列表。内核对未注册的 kind 兜底放行并保留其版本、引用与指纹，因此官方版本加载含这些组件的项目不会失败，也不会丢失数据。

### 2.2 术语表结构

**逐字段镜像上游 PR #1137 的 `dev.koharu.glossary`**，只有组件 kind 不同。这不是偷懒，是 `docs/extending-koharu.md` 第 5.3 节的要求：本地数据结构必须能无损映射到上游可能的实现，这样将来迁移是数据搬运而不是重新翻译。

镜像的部分：

- 顶层：启用开关、源语言、目标语言、源指纹、条目列表
- 条目：稳定标识、原文、译文（可空）、分类、启用状态、置信度、出现次数、样例、原文来源、译文来源、是否出现在最近一次扫描中
- 分类枚举七态：人物、地点、组织、物品、能力、术语、其他
- 来源枚举四态：检测到、自动、用户、导入
- 归一化：NFKC 归一化后折叠空白、转小写；去重键是「归一化原文 + 分类」
- 约束：原文与译文长度上限、样例条数上限与单条上限、分类与标识唯一性

需要额外加一个字段：条目需要携带一个可选备注，用于说明这条术语的适用情形（例如「只在战斗场景指武器，日常场景指工具」）。上游没有这个字段，属于本地扩展，将来迁移时它是唯一需要丢弃或转换的内容。

**`revisioned` 派生宏支持 `Vec` 字段**（上游的同一结构用了 `entries: Vec<GlossaryEntry>`），因此不需要手写序列化三件套。

标识类型使用带时间有序性的 UUID，与上游一致，避免迁移时重新生成标识。工作区的 `revision` 依赖已启用 `uuid` 特性，`uuid` 依赖也已启用时间有序与序列化特性，因此这个标识新类型可以直接派生，不需要手写实现。工作区里两者都已存在，只需在流水线 crate 的依赖清单里各加一行。

组件必须实现来源读写方法。原因是它既要能被界面命令写入（普通提交），也要能被翻译阶段写入（带生成信息的提交），后者会被内核的来源校验拒绝，除非组件支持设置来源。

**不声明记录引用与二进制引用**：术语表是纯数据，不引用其他实体，也不持有资源。这是它相对页面切片组件的关键简化——引用一致性是硬校验，声明错了会导致项目打不开，不声明则没有这个风险。

### 2.3 角色卡结构

自由文本，带启用开关。字段：一个字符串。上限参照文本组件的既有上限。

不做结构化（人物列表、称呼规则分字段）。理由：结构化的收益是能做「称呼一致性」这类自动检查，但当前没有校验器消费这些字段，只有模型消费，而模型对一段结构清晰的散文理解得不差。将来若真的写了校验器，再拆分不迟——`revision` 机制支持这种演进。

### 2.4 全局层

**不设全局术语表。**

参考实现的三层优先级（系统术语包 < 用户全局 < 书籍级）是为 2660 组合的术语包服务的，那是数据集需求。本仓库不引入数据集（见仓库约束中关于不提交数据集的条款），系统层不存在，三层优先级就退化成两层，多出来的那一层只增加排查成本。

跨项目复用通过显式的导出与导入实现，而不是隐式的作用域优先级。用户明确导出一份、明确导入到另一份，意图清晰；隐式优先级会让「为什么这条没生效」变成常见问题。

角色卡同理。

## 3. 注入

### 3.1 通道选择

按 `docs/extending-koharu.md` 第 2.8 节，翻译层不存在 trait 扩展点，可用的公开通道只有请求结构上已存在的字段。经评估：

| 内容 | 通道 | 理由 |
| --- | --- | --- |
| 术语表 | 语境条目 | 原文与译文成对，逐条对应。放进载荷里是离散条目，模型不会把对照关系读错 |
| 角色卡 | 附加说明 | 自由散文，与「语气、约定、禁止项」同类 |
| 上下文滑窗 | 语境条目 | 同术语表，且其内容本身既是术语也是对照 |

**术语表与上下文滑窗合并进同一个语境条目列表**，术语表在前。合并是语义自洽的：滑窗里的译文天然已经应用了术语表，两者不会矛盾。排序按「术语表优先、其次按页序」确定，保证同一页每次运行产生的载荷完全一致。

分类标签在这一通道上会丢失（语境条目只有原文与译文两个字段）。接受这个损失：分类主要服务于术语抽取与界面筛选，注入时「原文到定稿译文」这一对本身已经足够。

### 3.2 触发条件与预算

一次翻译请求携带的附加内容有上限，否则会挤占真正要翻译的文本：

- 术语表只发送**原文确实出现在本页待译片段中**的条目。全文匹配，不做模糊匹配。模糊匹配（编辑距离、倒排索引）复杂度高、收益低，而且会引入「匹配到但其实不是同一个词」的误伤。
- 注入前按预算截断，预算为固定字节数。术语表优先被截断（它有明确的定稿），其次是滑窗从最早一页开始丢。
- 整页没有任何条目命中时，不注入任何内容，避免出现空的语境段。

### 3.3 服务商能力

部分服务商不接受提示词（纯机器翻译类），它们会静默丢弃全部注入内容。必须在注入点按服务商判断并对不支持者关闭，不能让用户自己发现功能没生效。

判断放在发起注入的位置（一处），不要扩散到界面层。界面最多做一次提示，说明当前服务商不支持。

**占位符保护方案暂不实现。** 纯机器翻译类服务商可以通过「请求前把命中术语替换为占位符、返回后还原」的方式获得同样的术语一致性。这是参考实现里最巧妙的一个设计，但它需要在每个服务商文件里插入逻辑，属于红色位置。留待上游提供统一能力后再评估。

### 3.4 唯一的黄色改动

注入逻辑落在翻译阶段的处理函数内，约六行：读取项目组件、筛选、排序、预算截断、写入请求的语境条目与附加说明。

按第 3.2 节判定为黄色。理由：上游将来重写同一处时，本地改动的意图与上游完全一致（都是「把项目术语送进提示词」），差异只在读哪个组件，因此合并冲突是可解的语义一致，而不是两套实现竞争。

界面层与命令层全部是绿色：新增文件、新增命令、新增面板。

## 4. 界面

### 4.1 位置

**右侧栏新增第三个标签页。**

现状是右侧栏只有「属性」与「智能体」两页，宽度为窗口的约四分之一。术语表是项目级列表型内容，宽度合适，且与「属性」页的图层选择无关，因此独立成页而不是塞进属性页。

不放在活动中心：那里是瞬时的运行进度与下载浮层，完成后即消失，不适合承载需要反复编辑的内容。

不放在设置页：设置页承载的是全局配置，术语表是项目数据，放进去会造成作用域混淆——这正是当前「翻译指导」已经在文档里被特别说明为全局的原因。

### 4.2 结构

两个区块，共享一个启用开关。

**顶部状态行**：启用开关 + 一行提示，说明当前项目共有多少条术语、其中多少条会在本页命中。参考实现的实测经验是：没有这行提示，用户不会主动去发现待办事项。

**术语表区块**：
- 列表，每行一项：原文、译文、分类、启用状态、来源标记（用户 / 导入 / 自动）
- 人工编辑过的行有明确视觉标记，且重跑翻译时不会被覆盖
- 每行操作：编辑、启用禁用、删除
- 空条目状态：说明如何添加，以及可以从已有译文一键学习

**角色卡区块**：多行文本域 + 字数提示。

**底部操作**：添加术语、导入、导出。

**从译文学习**：作为第二期。做法是比对机器上次输出与用户之后的手动编辑，把差异中暴露的术语作为待确认项。参考实现的实测是自动改写译文会破坏更多好行，所以只提议、不自动应用。这一期只做「提议」这一半。

### 4.3 单个气泡的快速套用

第二期。在图层编辑器的译文输入框上方加一个「从术语表插入」按钮，列出本页命中的术语，点击填入。数据链路已经具备（气泡有原文与译文，场景里有项目组件），成本低。

### 4.4 文案

新增一个顶层命名空间，插入到按字母序排列的合适位置。共九个语言文件需要手工编辑，仓库没有提取工具。测试只校验英文，其余语言缺失时回退到英文，不会崩。

## 5. 维护

### 5.1 数据链路

界面状态走查询缓存，与项目身份绑定，项目切换时随既有刷新链路一起失效。**不放进全局 store**：全局 store 没有项目维度，切换项目时需要额外清理，容易漏。

命令层新增读取与写入两条，复用已注册的项目状态与画布通道，不新增状态注册。写入沿用现有编辑命令的模式：取项目锁、构造场景提交、记录提交、同步画布、推送画布通道。

新增命令需要改动命令收集宏一处，登记两行；命令体放在新文件中。

协议文件由仓库自带的生成器重新生成，会自动出现对应类型与调用签名。

### 5.2 撤销与重做

**自动获得。** 术语表存为场景组件，所有写入都是场景提交，因此既有的撤销与重做命令直接覆盖它。这是选择存场景而非存配置的主要收益之一——配置文件的写入没有撤销。

### 5.3 人工成果的保护

人工编辑过的术语与译文，来源标记为用户，重跑翻译时不被覆盖。场景的来源机制已经内建了这个能力，翻译阶段现有的「跳过用户已编辑译文」判定就是同一个模式，直接沿用。

术语表条目被删除后重新出现（例如重新扫描检测到同一术语）时，恢复为关闭状态而不是自动启用，避免打断用户已经整理好的结果。

### 5.4 导入导出

导出为制表符分隔文本，一行一条，原文、译文、分类、备注用制表符分隔。选文本格式而不是 JSON 的理由是它可以被人直接编辑和版本管理，符合「术语表是长期人工维护的资产」这个定位。导入时做冲突检测：标识相同的按人工来源优先，标识缺失的新条目追加，其余情况报告给用户而不是静默覆盖。

## 6. 已知限制

1. **纯机器翻译类服务商完全无效**，且无法在界面之外提示。只有三个服务商属于此类。
2. **分类标签不会出现在提示词里**，只用于界面筛选与排序。
3. **没有术语自动抽取**。原因见第 7.2 节。
4. **没有翻译缓存**。因此不存在缓存失效问题，但也意味着每次改术语表都要重新翻译全书才能看到效果。界面上必须让这一点可预期。
5. **若将来把翻译阶段改为跨页并发**，上下文滑窗不能继续依赖「上一页已提交」这个前提，需要改为显式维护按运行序号的队列。术语表不受影响（每次运行开始时快照一次即可）。**这是并发策略的前置约束，两者必须一起决策。**
6. **载荷预算的截断是静默的**。用户不会知道这一页只注入了部分术语。第一期接受，应在状态行显示命中数与总数。

## 7. 与上游的关系

### 7.1 当前状态

上游仓库中，术语表是一个开放的功能请求，维护者明确表示该功能仍然缺失，因此需求本身是被认可的。但已有两个社区实现提交，均未合并；其中一个被维护者以「拆分大 PR」的理由要求重做，重做版本随后被贴上负面标签并关闭，未给出书面原因；另一个至今无人评审。

**因此不能指望上游的实现作为稳定契约，只能作为数据结构的参照。** 这正是本文第 2.2 节选择逐字段镜像它的原因——镜像的是一份已经公开的、被上游代码接受过的形状，不是某个可能被放弃的分支。

### 7.2 为什么不实现术语自动抽取

参考实现的抽取依赖一个专门的实体识别模型。本仓库不引入模型权重（见仓库约束），也不改动流水线的阶段图（阶段枚举与依赖关系是封闭的，加入新阶段需要改动多处上游文件）。

更实际的原因是：抽取的价值依赖于「自动产出的候选必须经人工确认才生效」这个前提，而人工确认的界面本身就是主要工作量。**先做人工维护的闭环，再考虑自动化**，否则会得到一堆没人审的候选词。

### 7.3 迁移路径

上游实现同类功能时，按仓库约定放弃本地实现并迁移数据。具体动作：

1. 本地组件数据仍可读取，因为内核对未知组件宽容
2. 写一次性脚本，把本地组件的数据写入上游组件
3. 删除本地组件的读写代码

迁移是数据搬运的前提由第 2.2 节的镜像设计保证。届时需要人工处理的两处：条目备注字段上游没有，需决定丢弃还是塞进上游的上下文字段；角色卡没有对应概念，需决定丢弃还是用上游的附加说明承载。

### 7.4 逐项对比后保留差异

上游同类功能可用后，逐项对比保留上游未覆盖的部分，删除已覆盖部分。特别注意不要保留两套术语表并存——那比缺少功能更糟。本地真正独有的是：角色卡、以及纯机器翻译服务商的界面提示。
