# 翻译上下文：审计之后的设计细化

本文是 `docs/series-translation-assets-audit.md` 的下级文档。那份审计已经定了归属（漫画层）、注入通道（作用域管线）、编辑入口（章节管理页）与存储形态（术语表存独立文件）。**本文不重复那些结论，只补充审计未覆盖的部分，并把审计中省略的取舍论证补全。若两者冲突，以审计为准。**

扩展的形态约束见 `docs/extending-koharu.md`。

---

## 1. 当前请求粒度：逐页单图，不是批量多图

这一点必须先钉死，后续所有设计都建立在它之上。

一次翻译请求的内容是：

| 载荷 | 内容 | 出处 |
| --- | --- | --- |
| 图片 | 该页的 `source` 资产，一张。最长边缩到 2048，转 RGB，JPEG 质量 88，base64 内联 | 翻译阶段取页级 `source` 角色图片 |
| 文本 | 该页文本组内**所有**非空原文，按阅读顺序打包成一个 `segments` 数组，逐条编号 | 翻译阶段遍历文本层 |
| 输出 | 一个 JSON 对象，`translations` 数组与输入编号严格一一对应，条目数与编号范围都被模式锁死 | 输出模式构造 |

**「批」是页内的文本批，不是多图批。** 图片尺寸上限本身也排除了多图合并的可能。

### 1.1 已经存在的上下文，半径只到本页

| 层次 | 现状 | 系统提示词中的对应约束 |
| --- | --- | --- |
| 页内文本上下文 | 有。同一页的片段在一个数组里按阅读顺序排列，能解析页内的代词与省略 | 明确要求只用相邻片段做消歧与连贯，不得合并或拆分片段 |
| 页内视觉上下文 | 有。原图提供说话人身份、语气、版面布局、OCR 歧义 | 要求把原图当视觉上下文用，但**不得**把图里出现而输入片段里没有的文字加进译文 |
| 跨页文本上下文 | **完全没有** | 无 |

关键判断：**页内上下文是当前唯一的上下文来源，而它连不上一页。** 后文的全部设计都是为了补上这一段。

### 1.2 一个必须避免的误解

页内视觉上下文承担的是**页内消歧**。跨章与跨页的上文承担的是**跨页称谓与语气一致性**。两者不是同一件事，不能互相替代。

因此不要把上文做成术语表的替代品：术语一致性由人工资料负责，上文负责的是「模型看到自己刚翻完的写法」。

## 2. 上下文的三层来源

| 层 | 内容 | 生命周期 | 冷启动时 |
| --- | --- | --- | --- |
| **人工资料** | 翻译指导、术语表 | 漫画级，人工撰写 | **有** |
| **章内上文** | 本章已翻页的双语对照 | 每次运行派生 | 第一个无、之后有 |
| **跨章上文** | 上一章末尾的双语对照 | 每次批量派生 | 连载第一章无、之后有 |

### 2.1 第一批没有上文，靠人工资料

这是结构性事实，不是缺陷。**人工资料就是冷启动机制。**

翻译指导与术语表在第 1 页就能提供风格约定与专有词的定稿，不需要任何历史译文。

**不做角色卡。** 切片无法保证把说话人完整地留在同一页——气泡的尖尾可能落在上一页，人脸可能被刀口分开。说话人归属本身就不可靠，描述「谁用什么语气说话」的资料因此没有可靠的锚点，注入进去只会占用预算。术语表不受影响：词条靠文本匹配定位，与说话人归属无关。

这决定了实现顺序：**人工资料的闭环必须先做完，自动化派生才有意义。** 反过来做会得到一批无人审核的候选词。

### 2.2 章内上文

从当前页往前回溯若干页，取该页文本组内已成对的原文与译文。取「已翻好的」而不是「所有」，因为来源机制已经保证人工编辑过的译文质量最高，应优先采用。

回溯页数是一个预算问题，不是正确性问题。默认值参考社区实现取 4 页，可由用户在漫画层设置里调整。

### 2.3 跨章上文

**难点**：内核同一时刻只允许一个活动项目，章项目是彼此独立的工程，场景互不可见。要读上一章的场景，必须把它打开。

**但打开不等于激活。** 工程库提供的是「按名字打开并返回」与「替换当前活动项目」两个独立操作，因此可以打开任意章、读它的场景、然后直接丢弃，**不触碰当前活动项目**。这让跨章上文不需要任何换章空档，也不打扰正在跑的那一章。

**结论：趁本章还是活动项目时读它自己的尾部。** 批量循环本身就是「开一章、跑完整项目范围、等作业结束、下一章」，每章处理完的那一瞬间它仍然是活动项目，此时读出它的双语尾部、写入旁挂文件、留给下一章使用：

```
批量开始前（预扫描，两趟）：
    第一趟：逐章打开 → 收集全部原文（供术语匹配，见 §4.3）→ 丢弃
    第二趟：逐章打开 → 读出其双语尾部
            → 写入「章序号 + 1 的那一章」的跨章上文文件 → 丢弃
批量循环中：
    打开本章 → 替换活动项目 → 处理 → 等作业结束
    从当前活动项目读出本章的双语尾部
    → 覆盖写入「章序号 + 1 的那一章」的跨章上文文件
```

跨章上文文件按**目标章的章序号**命名，不按处理顺序。预扫描那一趟建立的是「磁盘上已有译文」提供的基线，循环里那一趟用刚翻完的鲜度覆盖它。

旁挂文件与漫画索引、术语表文件同级，复用同一套旁挂机制，零内核改动。

**成本**：预扫描使每章被打开两次（一次预扫描、一次处理），跨章上文不额外增加打开次数。总计每章两次打开，与是否启用跨章上文无关。若将来放宽单活动项目限制，这两趟可以合并成一趟。

### 2.4 上一章的判定

**按章序号，不按处理顺序。** 上一章是「序号小于本章且最接近本章的那一章」，与用户勾选的顺序、批量实际执行的顺序都无关。

理由：章序号是作品结构的客观顺序，处理顺序是用户这次操作的意图。用户可能只勾选第 24 章，也可能乱序抽查。语义上的「前文」由作品结构决定，不由操作顺序决定。24 章的前文必定来自 23 章，即使本次批量只处理了 24 章。

这个判定要在预扫描阶段完成，因为跨章上文必须在批量开始前就写入，不能等到上一章被处理。

### 2.5 跨章上文的两级降级

1. **上一章没有译文**（用户只勾选了后面的章，或上一章标记为完成但实际没跑过）：读到的双语对照为空，自然降级为无跨章上文，退回人工资料。
2. **上一章译文数量超过预算**：从最早的一条开始丢，保留最近的。因为称谓一致性看的是最近的写法。

两项降级都不需要用户干预，也不需要报错。上下文是增强手段，缺失时应当安静退化。

### 2.6 跨章上文存什么

存**最近若干条双语对照**，不存术语。理由见 §1.2：术语一致性由人工资料承担，跨章上文负责的是最近写法的一致性。存了术语会与术语表重复，并让渲染出的指令变长。

### 2.7 上文的两种内容形态

回溯页数由用户在漫画层设置里给出，因为合适的页数取决于模型与作品，只能实测确定。需要确定的是回溯内容包含什么，有两种形态。

**形态一：只注入译文。** 前若干页的原文与译文对照。零改动，散文通道即可承载，消耗只有文本量。

**形态二：注入译文与图片。** 除对照外，还带上那几页的画面，让模型知道角色长什么样、场景什么样、画风什么样。

形态二有一个硬约束：**翻译请求的图片位是单张，当前页已经占用了它。** 请求结构里那一个图片字段是可选的单值，不是列表。要发送多张图片，必须改动请求结构与六个服务商的部件渲染，属于红色区域。

拼接成一张长图也不可行。切片的目标高度是 1600、最长 2400，而发给视觉模型时最长边超过 2048 就降采样。四页拼在一起会被压到每页约 512 像素，**当前页的细节被牺牲**，而当前页恰恰是最需要细节的——气泡检测与识别都在它上面。

相关的一个交叉点：切片最长高度 2400 大于图片上限 2048，所以最高的切片本来就会被降采样。做上文图片注入时这条要记住。

**形态一，本期实现。形态二不做。**

除了翻译层改动本身，形态二在当前工作流里收益也有限：切片不保证保留完整的说话人画面，前几页的画面能提供的角色视觉信息本就有限。而把前几页拼成一张长图会被图片尺寸上限压到每页约 512 像素，**当前页的细节被牺牲**，而当前页恰恰是最需要细节的——气泡检测与识别都在它上面。

形态二留作后续项，触发条件是：实测发现跨页的角色视觉特征导致的翻译不一致。届时再评估改动翻译层的代价，并在同一份设计里补上多图部件的渲染约定。

## 3. 注入通道：为什么只能走附加说明

翻译请求结构上有三个可用字段，加一个不可用的。审计已确定走作用域管线替换附加说明字段，这里补全**为什么另外两个不可达**。

| 字段 | 渲染位置 | 可达性 |
| --- | --- | --- |
| 目标片段 | 载荷的片段数组 | 语义错误，这是真正要翻译的内容 |
| **附加说明** | 系统提示词末尾的附加段 | **可达**。翻译阶段只认构造运行器时拿到的配置，而作用域管线可以替换该配置，公开 API 组合即可，不需要改动流水线 |
| 语境条目 | 载荷的语境数组 + 系统提示词中对应的约束段 | **不可达**。这个字段的赋值点在翻译阶段内部，改它就是改流水线 |
| 目标语言 | 语言标签 | 语义错误 |

**这是审计结论的关键支撑**：附加说明字段是唯一一个既能表达内容、又能通过公开 API 换掉的通道。语境条目在语义上其实更适合术语表（成对结构、离散条目、还带「不要回译这些条目」的现成规则），但它没有可达路径。

代价是内容必须渲染成散文。参考实现把术语表作为结构化数据注入并配合本地匹配，走散文会损失这个收益——但见 §4.3，作用域管线反而能更好地补偿。

### 3.1 走散文通道必须自己补的规则

系统提示词里那段约束是随语境条目字段一起出现的，走附加说明通道时它不会出现。因此渲染出的文本必须**自带**「以下是参考资料，不要翻译、不要输出、不要复述」这句约束，以及「不要把参考资料里的译名当作待译文本」这句澄清。

这是走散文通道最容易漏掉的一步，会直接导致模型把参考译名当成待处理内容。

### 3.2 四段内容的拼接顺序

作用域管线把四段内容拼进同一个字段，顺序会影响模型的取舍权重：

| 序 | 内容 | 性质 |
| --- | --- | --- |
| 1 | 漫画级翻译指导 | 本作的风格约定，用户手写 |
| 2 | 术语表（仅命中条目） | 硬约束 |
| 3 | 上下文上文 | 参考材料，权重最低 |

这个顺序的逻辑是「一般到特殊，参考垫底」：先声明这本书的规矩，再给不可违反的译名，最后给可模仿的先例。用户全局指导排在这三段之后，作为跨作品的个人口味兜底。

**尚未实测。** 不同模型的指令权重行为不一致，顺序应当作为一项可在漫画层设置里调整的参数暴露给用户，而不是写死。

## 4. 匹配与预算

### 4.1 只发送命中的条目

整部漫画的术语表可能有几百条，全部塞进提示词会挤占真正要翻译的文本。必须只发送原文确实出现在待译内容里的条目。

匹配规则：**全文匹配，不做模糊匹配。**

模糊匹配（编辑距离、倒排索引）复杂度高、收益低，而且会引入「匹配到但其实不是同一个词」的误伤。术语表是人工维护的资产，用户会自己把词条写准；引擎需要做的只是筛掉用不上的，不是猜用户想表达什么。

**多词术语任一词元命中即算命中。** 人名与专有名词在正文里常以简称出现：作者写一次全名建立设定，之后只叫名（`Jack Hansen` 的 `Jack`）。要求整串会让那些页拿不到定稿译名，而译名在页与页之间不一致是读者一眼能看出的缺陷，所以宁可多注入一条词条。这个放宽的代价是两个不同角色同名时都会命中——纯字符串匹配无法区分「同一角色的简称」与「不同角色同名」，需要精确时把简称单独写成一条词条。

拉丁文字与西里尔文字要求词边界，避免 `Ann` 命中 `Anna`，也避免放宽后的 `Jack` 命中 `Jackhammer`；中日韩文字关闭词边界，按子串匹配，因为这些文字没有空格分隔。

归一化：NFKC 归一化后折叠空白、转小写，然后按「归一化原文 + 类别」去重。这与上游社区实现采用的规则一致。

### 4.2 字节预算

三样东西共用一个字节预算，按优先级分配：

1. **人工资料**（翻译指导 + 术语表渲染文本）——最高优先，它承载冷启动
2. **章内上文**——按页从近到远丢
3. **跨章上文**——按条从最早开始丢

超预算时的行为必须是静默的，但界面要显示「本章命中 N 条术语、注入 M 条」，否则用户无法判断为什么效果不稳定。

### 4.3 命中判定按章，不按页也不按全书

术语表匹配需要「待译内容」作为输入，而附加说明是**运行级**的一段散文：翻译阶段逐页发请求，但拿不到逐页变化的清单，一章共用一份。因此能判定的最小范围就是章。

- 命中判定基于**当前章**的原文，而不是单页原文
- 同一章内跨页出现的词条不会被漏掉
- 落在别章的词条对这一章没有用处，不注入

不按更大范围（全书）判定，是因为那会把别章的专有名词一起注入，对这一页既无用又占提示词。实测中一部维护正常的术语表在全书范围内命中率接近 100%，过滤几乎不起作用，注入量却按词表规模全额计入 token。

要真正做到逐页投放，得让术语表成为 `TranslationRequest` 的每页输入，也就是把术语表类型从应用层搬进翻译层、并让管线在每页上调用渲染。那是一次跨 crate 的类型边界改动，收益是省掉同章内未出现的词条，代价是类型搬移与绑定重新生成。

实现上，原文来源是各章工程里已有的文本组件，只读，不需要额外持久化。但内核同一时刻只有一个活动项目，所以「拿到原文」必须在运行开始前预扫描一轮逐章打开来收集——这与跨章上文机制共用同一趟预扫描，不额外增加成本。

## 5. 服务商能力

部分服务商接受完整提示词，部分只接受固定参数、不存在提示词概念。后者会**静默丢弃全部注入内容**——附加说明字段对它们完全无效。

必须在注入前按服务商判断并对不支持者关闭，界面同时给出一次提示。让用户自己发现功能没生效是最差的处理方式。

**这个判断落在渲染函数里，零改动。** 作用域管线在构造之前已经读到了当前配置，其中的模型选择包含服务商；渲染函数据此决定是否注入。批量期间服务商不变，因此判断在整个批次内有效。不要把这个判断扩散到界面层各处，也不要为了它改流水线。

界面侧只需在漫画层设置里显示一次当前服务商是否支持。

**暂不实现占位符保护方案。** 对不支持提示词的服务商，理论上可以在请求前把命中术语替换为占位符、返回后还原，从而获得同样的术语一致性。这是社区实现里最巧妙的一个设计，但它需要在每个服务商文件里插入逻辑，属于红色位置。等上游提供统一能力后再评估。

## 6. 存储结构

归属与文件划分由审计确定（漫画目录，术语表独立文件，与漫画索引同级）。这里只补审计未定的部分。

### 6.1 术语表逐字段镜像上游社区实现

上游已有两个未合并的社区实现，其中一个的术语表结构已被上游代码接受过。**逐字段镜像它的字段设计**，只有存放位置不同。

这不是图省事，而是 `docs/extending-koharu.md` 第 5.3 节的要求：本地数据结构必须能无损映射到上游可能的实现，这样将来迁移是数据搬运而不是重新翻译。若本地自行设计字段集，将来只能靠语义猜测去转换。

镜像的要素：

- 顶层：启用开关、源语言、目标语言、源指纹、条目列表
- 条目：稳定标识、原文、译文（可空）、类别、启用状态、置信度、出现次数、样例、原文来源、译文来源、是否出现在最近一次扫描中
- 类别七态：人物、地点、组织、物品、能力、术语、其他
- 来源四态：检测到、自动、用户、导入
- 约束：原文与译文长度上限、样例条数与单条上限、类别与标识唯一性

需要额外加一个字段：备注，用于说明适用情形（例如「只在战斗场景指武器，日常场景指工具」）。上游没有这个字段，属于本地扩展，将来迁移时它需要人工决定丢弃还是塞进上游的上下文字段。

标识用带时间有序性的 UUID，与上游一致，避免迁移时重新生成。工作区的版本化派生宏已启用标识特性，标识依赖也已启用时间有序与序列化特性，因此可直接派生。

**注意**：`Vec` 字段需要确认派生宏支持。社区实现用的是同一形态（一个列表字段加派生宏），若本仓库的派生宏版本相同则可直接沿用，否则需要手写序列化实现——参照场景内核文本组件里手写的范式。

### 6.2 术语表存独立文件，不进索引

索引是编排数据，会被频繁读、小幅写。术语表可能有数百条词条，每个词条都可能是一次编辑，**放进索引会让每次改一个词条都要重写整个编排文件**，并且人类可读性很差。

因此术语表存漫画目录下的独立文件，索引里只留一个引用字段（文件名或相对路径）。

角色卡曾计划同样处理，但它不做，原因见 §2.1。

## 7. 与上游的关系

沿用审计的结论，补充一点：

**逐字段镜像的收益现在比审计时更明确。** 审计写的是「迁移时把词条转成官方结构」，而镜像的做法把转换变成字段对字段的复制。差别在于：镜像之后，迁移脚本不需要理解语义，只需要换字段位置。

角色卡没有做，所以迁移时不存在这一项的决策。

## 8. 实施顺序

审计的第 1 至 5 步之后追加：

6. 章内上文派生（纯函数，只读场景，可单测）
7. 跨章上文旁挂文件读写（在批量循环里趁当前章仍是活动项目时调用）
8. 渲染函数接入上下文与命中过滤（仍是纯函数，可单测）
9. 从已有译文里发现候选词——最后做，只提议不自动写入

**第 6 至 9 步全部是新增文件或纯函数，不触碰红色位置，也不改动流水线。**

服务商能力判断放在渲染函数里，同样零改动：作用域管线在构造之前已经读到了当前配置，其中的模型选择包含服务商，渲染函数据此决定是否注入以及是否给出提示。批量期间服务商不变，因此这个判断在整个批次内有效。界面上的提示是纯前端。

## 9. 已知限制

1. **不支持提示词的服务商上自动关闭注入**并给出提示，只有三个服务商属于此类。它们的翻译质量不受影响，但也拿不到翻译指导、术语表与上文的任何收益
2. **类别不会出现在提示词里**，只用于界面筛选与排序
3. **没有翻译缓存**，因此不存在缓存失效问题，但改一次术语表就要重跑才能看到效果，界面必须让这一点可预期
4. **注入截断是静默的**，靠状态行显示命中数与注入数缓解
5. **不注入上文图片**（形态二已决定不做）。模型只能看到当前页画面与纯文本上文
6. **若将来把翻译阶段改为章内跨页并发**，章内上文不能继续依赖「上一页已提交」这个前提，需改为按运行序号维护队列。**这是并发策略的前置约束，与跨章上文机制无关但同样必须先定**
7. **收集全章原文需要预扫描逐章打开**，与跨章上文共用同一趟扫描。若将来放宽单活动项目限制，这两处可以合并成一次扫描
